# Mutation testing stays manual/local, not a CI gate

- Status: accepted
- Date: 2026-10-08

## Context

`mutmut` (ADR-0015) re-runs the relevant test file(s) once per surviving candidate mutant, which scales with the number of mutable branches in the target module(s) — materially slower than a normal test run, and slower again than the existing integration-test CI job. The lab wants a mutation report with surviving mutants classified (real gap / equivalent / acceptable) for `DEFENSE.md`, reproducible via `make mutation` — it doesn't ask for mutation testing to gate every PR.

## Decision

Mutation testing runs manually via `make mutation`, not as part of the CI pipeline that gates PRs into `main` (`standards/DEFINITION_OF_DONE.md`'s existing checks: lint, unit tests, integration tests). It's run deliberately, once, to produce the report `DEFENSE.md` references, and can be re-run on demand whenever the target module's tests change meaningfully.

## Alternatives considered

A scheduled (nightly/weekly) CI job was considered as a middle ground — keeps the report fresh automatically without slowing down the PR feedback loop a blocking job would. Rejected as more infrastructure than this lab asks for: the requirement is a reproducible report and a `make mutation` target, not a continuously-maintained one, and a scheduled job is one more piece of CI configuration to maintain for a report that's realistically regenerated by hand whenever the audit step (top-3 weak-test findings) actually changes anything.

## Consequences

The mutation report can go stale between runs — it reflects the test suite's state as of whenever `make mutation` was last run, not necessarily the current `main`. This is accepted: the report is a point-in-time audit artifact for `DEFENSE.md`, not a live quality gate. If mutation score ever becomes something the team wants enforced continuously, revisiting this decision (and likely narrowing which module(s) run in CI) would be the natural next step rather than running the full suite on every PR.
