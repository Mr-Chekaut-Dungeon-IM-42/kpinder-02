# Postgres + SQLAlchemy + Alembic as the persistence stack

- Status: accepted
- Date: 2026-10-08

## Context

Lab-2 moves the backend from a scaffold with no persistence to real database integration across all three slices (`auth`, `matching`, `chat`). Two independent choices are bundled here because they're made together in practice: which database engine to run, and which Python library talks to it (query layer + schema-migration tooling). ADR-0005 already picked PostGIS over plain lat/lng *given* Postgres, but never argued Postgres itself against a non-relational or embedded alternative; no ADR has argued the ORM/migration tooling at all.

Constraints that shape both choices:
- `matching`'s candidate query needs a geo-radius filter (`ST_DWithin`), a `NOT EXISTS` anti-join against `SWIPE`, and a join against `UserInterests` for Jaccard scoring — relational joins and spatial indexing, not key-value lookups.
- The swipe→match race (ADR-0006) is resolved by relying on a real unique-constraint-triggered `IntegrityError` inside a transaction — this needs a database with transactions and constraints as first-class, enforced guarantees, not application-level checks.
- `standards/DEFINITION_OF_DONE.md` already requires "no PR changes a SQLAlchemy model without a corresponding migration in the same PR" — the project's process assumes SQLAlchemy + a migration tool before this ADR, which this ADR now makes explicit and argued rather than assumed.

## Decision

Postgres (with the PostGIS extension, per ADR-0005) as the only datastore; SQLAlchemy as the query/ORM layer; Alembic for schema migrations, generated from SQLAlchemy models and reviewed by hand before being treated as the source of truth for schema changes.

## Alternatives considered

**Database engine:**
- **SQLite** — zero operational overhead (no server process), trivial for local dev and CI. Rejected: no PostGIS equivalent for geo-radius queries (would force Haversine-in-SQL, already rejected in ADR-0005 for being the weaker option), and its single-writer locking model is a poor fit for the concurrent-transaction race central to swipe→match (ADR-0006) — the whole insert-and-catch-unique-violation mechanism assumes genuine concurrent transactions, which SQLite's lock model works against rather than with.
- **MongoDB / a document store** — attractive if the data were naturally document-shaped (one user, embedded interests). Rejected: `matching`'s core query is a multi-way relational join with a spatial filter and an anti-join, which is exactly the shape relational engines are built for and document stores fight against; a unique compound index can emulate the `MATCH` race-prevention constraint, but Mongo's lack of true multi-document ACID transactions (pre-4.x semantics still linger in tooling/mental-model terms) makes "insert-and-catch-unique-violation inside one transaction" a worse-supported pattern than in Postgres.

**Query/ORM layer:**
- **Raw SQL via `asyncpg`/`psycopg`, no ORM** — fastest, most transparent about exactly what query runs (directly addresses the audit's N+1 concern — there's no ORM lazy-loading to accidentally trigger one). Rejected: the project's vertical-slice `repository.py` convention (spec.md) already assumes a typed model layer per slice; hand-writing and hand-maintaining raw SQL strings across four tables with FK relationships, plus hand-rolling migrations, is strictly more manual work for a 2.5-week lab with no corresponding safety benefit — the N+1 risk is a *query-shape* discipline question (addressed in spec.md §3 directly: mandate `selectinload`/`NOT EXISTS`, not "avoid ORMs entirely"), not something only raw SQL can solve.
- **Tortoise ORM** — async-native, Django-like, lighter than SQLAlchemy. Rejected: smaller ecosystem/community than SQLAlchemy, weaker PostGIS/GeoAlchemy integration (PostGIS support is a core reason Postgres was chosen at all), and Alembic's migration-diffing is purpose-built for SQLAlchemy models specifically — pairing Tortoise with Alembic is unsupported, and Tortoise's own migration tool (Aerich) is far less mature.

## Consequences

SQLAlchemy's lazy-loading relationships are the single biggest footgun for the audit's "no obvious N+1" bar — every cross-table read in a slice's `repository.py` (candidates' interests, a match's messages) must use explicit `selectinload`/`joinedload`, never bare relationship access in a loop; spec.md §3 already mandates this for the candidates query specifically. Alembic migrations must be reviewed, not blindly autogenerated — autogenerate correctly diffs column/table changes but does not reliably infer PostGIS-specific details (spatial index type, SRID) without the migration author checking the generated script by hand. Running PostGIS everywhere (local `docker-compose`, CI testcontainers, hosted DB) is a consequence already accepted under ADR-0005, not a new cost introduced here.
